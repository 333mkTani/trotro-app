# Trotro staging service stack

This document defines the staging deployment contract for issue #23. The repository contains a dedicated [`render.staging.yaml`](../render.staging.yaml) Blueprint so staging resources are named separately from the existing production-oriented [`render.yaml`](../render.yaml). The staging Blueprint provisions a Node API, a dedicated schedule worker, a static admin site, a Redis Key Value instance, and a PostgreSQL 16 database.

> **Important:** Provisioning the Blueprint creates infrastructure, but it does not create or reveal provider credentials. Paystack, Firebase, Mapbox, and the CORS allowlist must be entered in the Render Dashboard as secret or synchronized values.

## Provisioning sequence

First, connect the repository and staging branch to a new Render Blueprint. Set the Blueprint Path to `render.staging.yaml`, review the resource names, and deploy the Blueprint. The database is private (`ipAllowList: []`), while the API and worker receive its connection string through `fromDatabase`. Render Postgres supports PostGIS; after the database is available, the migration command enables the required extensions as part of the migration history.

The API uses `preDeployCommand: npm run migrate` and exposes `/health` for liveness and `/ready` for dependency-aware readiness. Render should use `/ready` as the service health check. The schedule worker runs separately with `npm run worker:schedule` and uses PostgreSQL advisory locking so a restart or accidental duplicate worker does not run the same schedule cycle concurrently.

The admin site receives `VITE_API_URL` at build time. Set it to the staging API `/api` origin before the admin build runs, for example `https://trotro-staging-api.onrender.com/api`. Changing it after the build requires a new admin deploy.

## Required staging values

| Variable | Service | Handling | Purpose |
|---|---|---|---|
| `CORS_ORIGIN` | API | Render secret/config value | Comma-separated passenger, driver, and admin web origins; never `*` in staging. |
| `PAYSTACK_SECRET_KEY` | API | Secret | Paystack test-mode server credential for initialization, verification, transfers, and webhook checks. |
| `FIREBASE_SERVICE_ACCOUNT` | API and worker | Secret | Single-line Firebase Admin service-account JSON for phone verification and push notifications. |
| `MAPBOX_ACCESS_TOKEN` | API | Secret | Server-side Directions/Mapbox credential; never expose it through an Expo public variable. |
| `VITE_API_URL` | Admin | Build-time value | Staging API `/api` base URL. |

`JWT_SECRET` is generated by the Blueprint. `DATABASE_URL` and `REDIS_URL` are wired from the managed Render resources. `REQUIRE_REDIS=true` makes `/ready` fail until Redis is reachable, preventing a staging deployment from appearing healthy while operating without shared cache, rate-limit, and realtime support.

## Verification

Run the repository smoke verifier from the backend directory after entering the staging values into the environment. It checks API liveness, database/Redis readiness, Paystack test credentials, Mapbox credentials, and Firebase Admin credentials without printing provider response bodies or secret values.

```bash
cd rork-trotro-ride-clone-main/backend
BASE_URL=https://trotro-staging-api.onrender.com \
PAYSTACK_SECRET_KEY=... \
FIREBASE_SERVICE_ACCOUNT='{"type":"service_account",...}' \
MAPBOX_ACCESS_TOKEN=... \
npm run verify:staging
```

The command is intentionally strict. A missing credential or failed provider check exits non-zero. Store the values in CI/Render secret storage rather than in shell history when running it in automation.

For local dependency verification, use the existing Docker Compose stack:

```bash
cd rork-trotro-ride-clone-main/backend
docker compose up -d db redis
docker compose --profile tools run --rm migrate
```

Then set `DATABASE_URL`, `REDIS_URL`, and `REQUIRE_REDIS=true` for the API and verify `GET /ready`. The local database uses the same PostGIS image family as the staging database, which keeps spatial migration behavior close to the deployed environment.

## Rollback and recovery

To roll back an application deploy, use the Render service’s previous successful deploy for the API, worker, and admin site. Do not roll back the database independently after a migration has been applied unless the migration’s documented forward-fix or restore plan has been reviewed. Before any migration change, capture a database backup or snapshot and record the deployed commit, migration version, and worker version.

If `/ready` fails after deployment, inspect the database connection, Redis connection, migration output, and secret presence in that order. A failed readiness check should keep the API out of traffic while `/health` remains useful for process liveness. If a provider credential fails, rotate the affected secret and redeploy only the dependent service. For a complete staging teardown, delete the Blueprint resources from the Render Dashboard after confirming that no acceptance-test evidence or database snapshot is still required.

## Acceptance evidence

Record the following for issue #23: Blueprint deployment URL and commit, API/worker/admin service URLs, database and Redis health, migration version, `/health` and `/ready` responses, smoke-verifier output, Paystack test reference, Firebase verification result, Mapbox verification result, CORS origin list, and rollback owner. Never attach raw secret values or unredacted provider responses.
